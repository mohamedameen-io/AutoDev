# Release Retrospective: v0.33.0

**Date:** 2026-05-16
**Release tag:** v0.33.0
**Postmortem author:** AutoDev maintainers
**Triggering event:** Plan-phase unblock (Tier A of the v0.32.0 retrospective). The prior release exposed a recurring pattern where the architect produced internally-consistent plans that the file-existence validator rejected because of cross-task references to soon-to-be-created files; the architect could not self-correct because the prompt did not document the contract the validator was enforcing.

## Summary
v0.33.0 closes Tier A of the v0.32.0 retrospective by aligning the file-existence validator with the architect prompt on a single rule: `[new]` is plan-global. A task that references a file declared `[new]` by any sibling task in the same plan validates green; the architect prompt explicitly states this rule and forbids producing investigation-notes deliverables that the phase-review diff cannot see. A new ledger op surfaces each plan-global admission so downstream forensics can distinguish "real on-disk file" from "deferred to creator-task" admissions.

## 1. What shipped
- A1 (plan-global `files_new` aggregation): **landed** — `_collect_plan_new_files` helper added to `src/orchestrator/file_existence_validator.py`; `validate_files_exist` admits any path declared `[new]` by any task; resolutions are surfaced via an optional out-channel so the async caller in `src/orchestrator/plan_phase.py` can emit the new ledger op.
- A2 (architect documents the `[new]` rule): **landed** — anchor `[new] PREFIX RULE` added under the CANDIDATE FILES section.
- A3 (architect forbids investigation-notes deliverables): **landed** — anchor `NO INVESTIGATION NOTES` added to the same section.

## 2. What changed
Matches the v0.33.0 CHANGELOG entry:
- Validator no longer rejects cross-task references when the file is declared `[new]` somewhere in the plan.
- Architect prompt carries the `[new] PREFIX RULE` and `NO INVESTIGATION NOTES` anchors.
- New ledger op `path_validation_resolved_via_plan_global` with payload `{task_id, path, declaring_task_id}`.

## 4. What's NEW
- **Caused by the fix itself:** plan-global admission is permissive by design, so a typo in a task's `files_new` could mask a typo in a later task's `files` if both happen to canonicalise to the same wrong string. Mitigation: the ledger op makes the admission auditable post-hoc, but no synchronous check on the canonical-but-misspelled case.
- **Below the most-urgent layer at the prior retrospective time:** Tier B (execute-phase hallucination guard + sparse-checkout sibling headers + drift convergence exit) is now the head of the queue. The v0.33.0 fix removes the plan-phase blocker, exposing the next layer.

## 5. What's the NEXT layer of failure?
**REQUIRED SECTION.** Speculate explicitly about what will surface AFTER the v0.33.0 fix ships. Input to v0.34.0 planning. At least three candidates.

- **Candidate 1:** Plan-global resolution leaks typo'd paths into the execute phase. Severity: Medium. Why we suspect: the validator now admits any path declared `[new]` somewhere in the plan, so two tasks that both misspell the same artifact name (e.g. `notes_artifcat.md`) will validate green and only fail later at execute-time when the consumer task can't find the file the creator task didn't actually produce. Falsifiable signal: a real run where `path_validation_resolved_via_plan_global` was emitted for a path that the execute phase later reports as missing on disk during dispatch.
- **Candidate 2:** Architect continues to propose `.md` notes deliverables despite the prompt. Severity: Medium. Why we suspect: the rule is documented but not enforced — there is no validator-side rejection of `notes-*.md` or `*-investigation.md` paths, so a stubborn architect can still emit them. The CHANGED-since-v0.32 retrospective discipline expects the architect to have internalised the rule, but a single LLM regression could undo it silently. Falsifiable signal: any post-v0.33 ledger that contains `path_validation_resolved_via_plan_global` payloads where `path` matches `notes-*.md` / `*-investigation.md` / `notes/*` patterns.
- **Candidate 3:** Telemetry sample-count from `path_validation_resolved_via_plan_global` after the first prod run is either zero (architect never produced cross-task plans, suggesting the rule is over-engineered) or unreasonably high (the architect now emits cross-task references for files that should have been declared on the consuming task too, suggesting under-engineering). Severity: Low. Why we suspect: this is the first release that admits this admission path, so the prior is wide. Falsifiable signal: sample count over the first 50 prod runs; expect 5–25 admissions in steady state if the contract is calibrated correctly.
