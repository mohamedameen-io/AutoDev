# v0.37.0 retrospective — Tier H

Cascading-failure closure. Five phases land together because they
reinforce each other against the compounding stuck-recovery pattern
observed in real-world enterprise runs (blind evidence → bad refines
→ unbounded corrective fanout → infrastructure failures hiding as
per-task blocks → wrong adapter wasting operator quota).

## 1. What shipped

- **H1** (evidence-capture body forwarding):
  `src/orchestrator/execute_phase.py` gains `_build_recent_evidence_block`
  near the existing `_build_recovery_hint` family. The helper reads
  the freshest reviewer / test / coder evidence files for the failing
  task, pulls `raw_response` (falling back to `output_text`), truncates
  each kind to `recent_evidence_max_chars_per_kind` from the tail, and
  prefixes with labelled headers `REVIEWER_RAW:` / `TEST_RAW:` /
  `CODER_RAW:`. Both `recent_evidence=` call sites — the architect-
  consult site in `_dispatch_architect_consult` and the stuck-critic
  site in `_escalate_stuck_to_critic` — swap their inline `web_context_block +
  reason` concat for the helper. Backward compat: `recent_evidence_max_chars_per_kind=0`
  OR an empty `recent_evidence_include_kinds` restores the legacy one-
  liner; pre-v0.31.0 evidence files lacking `raw_response` fall back
  to `output_text` then `""`.
- **H2** (per-phase correction-task cap):
  `src/orchestrator/corrective_parser.py:parse_corrective_direction`
  accepts `max_tasks`; both call sites in `execute_phase` compute
  `remaining_budget = max(0, max_corrective_tasks_per_phase -
  len(phase.corrective_task_ids))` BEFORE invoking the parser, so the
  cap is cumulative across architect-refine + phase-review-tournament
  rounds. On exhaustion the orchestrator emits
  `corrective_cap_reached`, marks `Phase.review_status="capped"`
  (new Literal value), and soft-blocks the originating task via the
  recovery-hint pipeline with `autodev requeue` / `autodev rewind`
  next-actions. `PlanManager.append_corrective_tasks` carries an
  independent defence-in-depth truncation that emits a distinct
  `defended=True` payload so divergent callers can't bypass the
  invariant.
- **H3** (test-runner capture-failed cross-task circuit):
  `InfraFailureCircuitBreaker` carries a second deque keyed off
  `record_test_diagnosis(task_id, diagnosis, ts)`. The existing
  `record_failure` / `should_halt` adapter-class semantics are
  preserved; `reset()` clears both streams while a new `reset_adapter()`
  clears only the adapter-class deque (so the test-diagnosis deque
  accumulates across intervening healthy adapter calls — the Unity-
  shape "10 tasks each with one capture_failed" pattern is now
  caught). Both retry-once and hard-fail branches of the existing
  `capture_failed` routing in `execute_phase` feed the breaker. Trip
  raises the existing `InfrastructureCircuitOpenError` so v0.29.0
  quarantine catch sites handle the test-diag trip identically.
  Task-state transitions widened so `coded` / `auto_gated` / `reviewed`
  / `tested` can move to `quarantined` (the H3 trip lands mid-test-
  slot when the task is in `reviewed`).
- **H4** (adapter trigger-context routing):
  `src/adapters/detect.py:_detect_trigger_context` reads `CLAUDECODE`
  / `CLAUDE_PROJECT_DIR` (claude_code wins) and `TERM_PROGRAM=Cursor`
  / `CURSOR_*` (cursor wins). Inserted as a NEW step between explicit
  `preferred` (still wins) and `AUTODEV_PLATFORM` env. The chosen
  adapter is healthchecked; on failure
  `detect_platform.trigger_context_unhealthy` fires and selection
  falls through to the next step. Every `detect_platform.selected`
  log line now carries `source` so post-run analysis can answer "why
  this adapter?" from logs alone. The new
  `adapter_respect_trigger_context` config knob is the escape hatch
  for operators who want pre-v0.37.0 precedence.
- **H5** (large-codebase auto-defaults): new modules
  `src/orchestrator/repo_size.py` (centralised `is_huge_repo(cwd)` with
  `git ls-files` fast path + `os.walk` fallback, lru-cached, threshold
  defaults to `index_full_rebuild_threshold_files=5000`) and
  `src/orchestrator/huge_repo_overrides.py` (knob-keyed resolver that
  emits the existing `huge_repo_multiplier_applied` telemetry op per
  scaled knob). `task_overrides.huge_repo_multipliers` default now
  covers all H1/H2/H3 knobs alongside the pre-existing
  `max_duration_s_per_task` / `max_diff_bytes` entries. Wired into:
  `Orchestrator.__init__` (circuit breaker construction reads scaled
  thresholds + window), `execute_phase` H1 evidence-cap site,
  `execute_phase` H2 cap sites.
  `src/qa/hallucination_guard.py` auto-unions a huge-cpp skip set
  (`**/PrecompiledHeaders/**`, `**/Generated/**`, `**/Intermediate/**`,
  `**/Engine/**`, `**/build/**`, `**/cmake-build-*/**`) when
  `is_huge_repo` AND the language profile shows ≥80% C/C++, emitting
  `hallucination_guard.huge_repo_cpp_paths_included`. Operator-
  provided `hallucination_guard_skip_dirs` still unions on top.
  `src/adapters/detect.py` bumps the `AUTODEV_LANG_WEIGHT` default
  from 0.0 to 0.5 when `cwd` is huge — language-weighted fitness
  engages by default. Trigger-context from H4 still wins because the
  precedence order puts it BEFORE the fitness-weighted path.

## 2. What changed

Matches the v0.37.0 CHANGELOG entry verbatim. Schema changes:

- New config knobs (defaults preserve previous behaviour on small
  repos): `recent_evidence_max_chars_per_kind: int = 4000`,
  `recent_evidence_include_kinds: list[str] = ["review","test","coder"]`,
  `max_corrective_tasks_per_phase: int = 8`,
  `corrective_cap_action: Literal["soft_block_phase","skip_corrective_round"]`,
  `test_diag_breaker_threshold: int = 3`,
  `test_diag_breaker_window_s: float = 600.0`,
  `test_diag_breaker_diagnoses: list[str] = ["capture_failed"]`,
  `adapter_respect_trigger_context: bool = True`,
  `huge_repo_overrides_disabled: bool = False`.
- `Phase.review_status` Literal gains `"capped"`.
- Task-state transitions: `coded` / `auto_gated` / `reviewed` /
  `tested` → `quarantined` newly allowed.
- `task_overrides.huge_repo_multipliers` default extended with
  `max_corrective_tasks_per_phase: 2.0`, `test_diag_breaker_window_s: 2.0`,
  `test_diag_breaker_threshold: 2.0`,
  `recent_evidence_max_chars_per_kind: 1.5`,
  `circuit_breaker_threshold: 2.0` (existing keys preserved).
- New ledger op `corrective_cap_reached` registered in
  `src/state/ledger.py`.

## 4. Next layer of failure

The six things we deliberately did not solve in v0.37 — surfaced
here because they are the highest-leverage follow-ups:

1. **`GuardrailEnforcer` does not read the H5 multipliers.** The
   defaults for `max_duration_s_per_task` and `max_diff_bytes` sit in
   the `huge_repo_multipliers` dict, but the enforcer reads
   `cfg.guardrails` directly and so the per-task duration cap and the
   per-task diff-size cap still bind to the small-repo defaults even
   on huge repos. Wiring the H5 resolver into the enforcer is the
   v0.38.0 follow-up.
2. **Architect-refine quality plateau under H1's richer evidence.**
   With the reviewer body now in-prompt, architect-refine produces
   better-targeted corrections, but those corrections are larger; the
   H5-multiplied `max_duration_s_per_task` may still bind on the
   largest cases. Expect "task timed out" to replace "reviewer
   NEEDS_CHANGES" at the top of stuck reasons.
3. **Soft-block backlog congestion.** H2's `soft_block_phase` funnels
   capped phases to manual triage, but `autodev status --blocked` has
   no bulk-resolve UX. A `--bulk-requeue` flag or per-phase resume
   command is the obvious next step.
4. **Cross-phase corrective leakage.** H2 caps per-phase; long multi-
   phase plans can still accumulate cap-after-cap. A plan-global
   corrective ceiling may be needed.
5. **H3 false-positives on legitimately flaky suites.** H5 widens the
   window on huge repos, but persistently flaky test runners (e.g.,
   cross-compile toolchains) may still trip. The likely v0.38
   intervention is per-diagnosis exponential backoff (auto-reset
   after N successful tests) rather than hard halt.
6. **H4 misclassification edge cases.** Terminal multiplexers (tmux,
   screen) or remote shells may pass through `TERM_PROGRAM` from the
   outer host even when the operator is running in a different inner
   adapter. The `adapter_respect_trigger_context=False` escape hatch
   exists; we need operator feedback on whether it's getting flipped
   routinely (signal that the heuristic needs tightening) or rarely
   (well-tuned).
