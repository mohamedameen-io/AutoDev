# v0.36.0 retrospective — Tiers D + E + F + G

Retries, budgets, forensics, spec hygiene. Largest of the four staged
releases following the v0.32.0 retrospective: nine findings landed
inline.

## 1. What shipped

- **G1** (spec validator): `src/orchestrator/spec_validator.py` is a new
  module exposing `validate_spec(path: Path)` and
  `validate_spec_text(text: str)`. The CLI's `autodev plan` short-
  circuits with exit code 4 when the intent text is empty, < 40 chars
  of non-whitespace, a scope-less one-liner, or missing any acceptance
  signal; `--skip-spec-validation` is the documented escape hatch.
- **D1** (rejection diagnosis): `PathValidationError` carries an
  `error_class` field; `file_existence_validator._classify_rejection`
  buckets paths into `new_md_deliverable` / `missing_on_disk`; the
  retry envelope's `render_rejection_history` collapses N sibling
  rejections of the same class into one design-class diagnosis
  paragraph followed by the path list. `_DIAGNOSIS_TEMPLATES` lives in
  `retry_envelope.py`; `diagnosis_for_class()` is the public lookup.
- **D2** (fuzzy hint suppression): `_RepoFileSnapshot.closest`
  consults `_hint_is_plausible` — suggestions whose top-level dir
  differs from the rejected path are suppressed; short paths under
  12 chars use cutoff 0.85 (was 0.7) for difflib.
- **D3** (structural-retry model): config field
  `agents.architect.structural_retry_model: str = "sonnet"`;
  `plan_phase_recovery.should_change_model_for_class` returns the
  configured model when the architect is on opus AND the rejection
  class is structural. The plan-phase retry loop mutates-and-restores
  `orch.registry["architect"]` for the single retry dispatch.
- **E1** (huge_repo_multipliers): default for
  `task_overrides.huge_repo_multipliers` flipped from `None` to a
  populated role-keyed dict; `execute_phase.delegate` emits
  `huge_repo_multiplier_applied` per dispatch when a role-keyed
  multiplier > 1.0 applies on a huge repo.
- **E2** (adaptive retry budget): `resolve_task_max_turns` gained
  `retry_attempt`, `retry_budget_multiplier`, and
  `retry_budget_cap_turns`; retry attempt ≥ 2 doubles the resolved
  budget, capped at 200 turns. Call site emits `retry_budget_scaled`.
- **F1** (plan-ledger ops): three new ops registered
  (`architect_attempt_failed`, `recovery_tier_attempted`,
  `path_rejection_recorded`). The `0 → 0` lie in the recovery
  breadcrumb is replaced with the real `base_max → retry_max` values;
  each of tiers 4–7 emits its own `recovery_tier_attempted` op
  carrying tier number, outcome, reason, and from/to state.
- **F2** (network probe retry): `adapters.base.NetworkProbeFailure`
  is the new structured exception. `claude_code._pong_probe` wraps
  `_pong_probe_once` in a retry loop sized by
  `cfg.adapters.probe_retry_attempts` (default 3) with exponential
  backoff. Auth failures short-circuit (no retry). CLI catches the
  exception at the `autodev plan` entry, exits code 5, surfaces
  `.suggestion`.
- **F3** (status surface): `_render_blocked_section` consults
  `_collect_recovery_outcomes` (parses the F1 ops from the ledger)
  and `_find_architect_dumps` (globs the debug dir); renders
  "Recovery Tier Outcomes", "Architect Attempts", "Archived
  Rejected Plans", plus the D1 diagnosis paragraph for the most
  recent rejection class.

## 2. What changed

Matches the v0.36.0 CHANGELOG entry verbatim. Schema changes:

- `PathValidationError.error_class: str = "missing_on_disk"` (in-memory only).
- `PriorError.error_class: str = "missing_on_disk"` (Pydantic; default-safe).
- `AgentConfig.structural_retry_model: str = "sonnet"`.
- `TaskOverridesConfig.huge_repo_multipliers`: now `dict[str, float]`
  with a populated default factory (was `dict[str, float] | None = None`).
- `TaskOverridesConfig.retry_budget_multiplier: float = 2.0`,
  `retry_budget_cap_turns: int = 200`.
- `AdaptersConfig.probe_retry_attempts: int = 3`,
  `probe_backoff_initial_s: float = 1.0`.

## 4. Next layer of failure

The five things we deliberately did not solve in v0.36 — surfaced here
because they are the highest-leverage follow-ups:

1. **D1 diagnosis library missing classes seen in production.** The
   classifier today recognises only `new_md_deliverable` and the
   generic `missing_on_disk` fallback. Real-run forensics likely show
   other shapes (renamed-but-not-tagged files, typo'd extensions,
   plan-level scope entries that became stale across commits). The
   ledger op `path_rejection_recorded` is the queryable surface — once
   we have enough samples to spot the cluster, add the templates.
2. **Huge-repo cost telemetry per run.** `huge_repo_multiplier_applied`
   records the per-dispatch decision but we do not aggregate the
   per-run additional cost (multiplier × base × dispatches). Until the
   aggregation lands operators can't tell whether the multipliers are
   under- or over-tuned for their actual workload.
3. **Ledger-line-count distribution.** F1 emits more ops per run than
   v0.35. Without a baseline distribution per release, we can't
   detect a per-run ledger size regression (the v0.32.0 fixture's
   ledger was 2.97 MB / 140 entries; v0.36's per-attempt + per-tier
   ops can multiply that on failure-heavy runs).
4. **Probe-retry success rate.** `network_probe_failed` emits per
   attempt AND on final failure. We have not yet built a dashboard
   that buckets "retried but succeeded" vs "retried and still failed"
   to validate the 3-attempt default. If success-on-retry-2 dominates,
   bump the default to 2; if final-failure dominates a particular
   network class, route earlier.
5. **Spec-validator false-reject rate.** The G1 rules are
   conservative but not zero-cost. The `spec_validation_failed` op
   carries the reasons; we need a sanity dashboard so operators can
   tell whether `--skip-spec-validation` is being used routinely (the
   front-gate is too strict) or rarely (it's well-tuned).
