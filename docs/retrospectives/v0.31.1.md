## 4. What's NEW
- **Caused by fixes themselves:** the new release CI is stricter and fails on missing `CHANGELOG.md` entries, which exposed older PRs in flight that did not include changelog edits. This is intended behaviour but feels like a regression to contributors.
- **Below the most-urgent layer:** the worktree cleanup (Phase 7) revealed that a few orchestrator paths leak temp directories on abort. Tracked but deprioritised behind the Blocker findings.
- **Upstream-invisible:** none in this cycle — every regression was self-inflicted, which is itself a finding.

## 5. What's the NEXT layer of failure?

This is the input to v0.32.0 planning. With the v0.31.1 fixes in place, here is what we expect to surface next:

- **Candidate 1:** Per-task autoreason cost ceiling at scale. Severity: High. Why we suspect: running A/B/AB plus three judges across dozens of tasks per run can exceed Cursor usage caps even on Pro plans, and the orchestrator does not currently throttle or estimate spend ahead of dispatch. Falsifiable signal: a real-world run aborting mid-execute with a usage-limit error from the adapter and no preflight cost warning in `autodev logs`.
- **Candidate 2:** Knowledge-base recall when task signatures don't match exactly. Severity: High. Why we suspect: the lookup uses signature similarity, but novel tasks won't have past matches; the agent will then either fall through silently or emit a generic plan. Falsifiable signal: a fresh run on a codebase with no prior history shows zero KB hits in `autodev logs` and the planner produces noticeably weaker plans than on the seeded test fixtures.
- **Candidate 3:** Test-runner diagnosis false positives on novel test runners. Severity: Medium. Why we suspect: the heuristic is keyed on pytest / jest output strings, so cargo, maven, gradle, go test, dotnet test, etc. may misclassify a green run as red (or vice versa). Falsifiable signal: a run on a non-pytest/non-jest project where `autodev` reports a passing test suite as failing in the structured result, or a failing one as passing.
- **Candidate 4 (optional):** RecoveryHint `commands_to_try` drift as new CLI subcommands ship without updating the hint catalog. Severity: Medium. Why we suspect: there is no test that asserts every command referenced by RecoveryHint actually exists in the current CLI registry, so the hint catalog can rot the same way the slash-command spec did. Falsifiable signal: `autodev` emits a recovery hint pointing to a subcommand that returns "unknown command" when the user runs it.
